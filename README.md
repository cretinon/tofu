# tofu — Proxmox VE guests with OpenTofu

Opinionated OpenTofu project provisioning **Debian virtual machines** and **unprivileged
LXC containers** on a **Proxmox VE** node, driven by two maps of objects (`var.vm` and
`var.ct`) so that adding a guest is a `.tfvars` edit instead of a resource copy/paste.

Everything a guest needs is managed by the code: the OS images are downloaded on the node
(PVE `download-url` API), the cloud-init snippets are rendered from the variables and
uploaded to the datastore, and the VM disks are imported from the downloaded images.

- **Tooling:** [OpenTofu](https://opentofu.org/docs/) ≥ 1.6 (`tofu` commands throughout)
- **Provider:** [`bpg/proxmox`](https://registry.terraform.io/providers/bpg/proxmox/latest/docs) `~> 0.74.0` (any 0.74.x patch release)
- **Guests:** Debian 13 (default) or Debian 12, per entry
- **State:** local (`terraform.tfstate`, git-ignored — see [State](#state))

## Architecture

| File | Contents |
|---|---|
| `providers.tf` | OpenTofu/provider version constraints and the `proxmox` provider block (endpoint, auth, TLS, temp dir, `ssh` block). |
| `variables.tf` | Every input variable, grouped by concern, with defaults and `validation` blocks. |
| `images.tf` | `proxmox_virtual_environment_download_file` — one image per `var.images` entry. |
| `cloud-init.tf` | The two `proxmox_virtual_environment_file` snippet uploads (`user-config`, `vendor-config`). |
| `vms.tf` | `proxmox_virtual_environment_vm` — one VM per `var.vm` entry. |
| `containers.tf` | `proxmox_virtual_environment_container` — one container per `var.ct` entry. |
| `outputs.tf` | Guest ids/names/addresses and the datastore ids of images and snippets. |
| `cloud-init/user-config.yaml.tftpl` | User data template (admin user, SSH keys, resolvers), rendered by `templatefile()`. |
| `cloud-init/vendor-config.yaml` | Vendor data: installs and enables `qemu-guest-agent`. |
| `terraform.tfvars.example` | Documented sample values — copy it to `terraform.tfvars`. |
| `.gitignore` | Keeps state, saved plan files and `*.tfvars` (secrets) out of git; `.terraform.lock.hcl` stays tracked. |
| `.terraform.lock.hcl` | Generated by `tofu init` and tracked: pins the provider version and its checksums. |
| `lib_tofu.sh` | Orchestrator wrapper: the `my_warp.sh` commands (`tofu_plan`, `tofu_check`, ...) and their safety guards. |
| `conf/tofu.conf` | Defaults for `TOFU_BIN` / `TOFU_DIR` / `TOFU_VAR_FILE` (the environment always wins). |
| `bats/tests.bats` | BATS suite: wrapper behaviour (mocked `tofu`) plus the project invariants (real `tofu`). |
| `functions.md` | Auto-generated function reference (`my_warp.sh --lib tofu --doc functions.md`). |
| `AGENTS.md` | Working instructions for AI agents in this repository. |

Resource addressing is keyed by the map keys, e.g.
`proxmox_virtual_environment_vm.debian_vm["web-01"]`, so renaming a key rebuilds that guest
while other guests are untouched.

## Prerequisites

### Proxmox VE side

1. **A user or API token** with the privileges needed by this project. `Datastore.AllocateTemplate`,
   `Sys.Audit` and `Sys.Modify` are required by the image download, `VM.Config.*`/`VM.Allocate`
   for the guests. To create a token:

   ```shell
   pveum user add terraform@pve
   pveum aclmod / -user terraform@pve -role PVEAdmin      # review/limit this role for production
   pveum user token add terraform@pve provider --privsep=0
   ```

   Some operations only work with password authentication (`root@pam`), which is why the
   project can also read `pve_username`/`pve_password`.

2. **Snippets enabled** on the datastore used for cloud-init (`Datacenter > Storage > local >
   Edit > Content > Snippets`). Without it, the snippet upload fails.

3. **SSH access to the node.** The provider uploads the snippets and imports the VM disk
   images over SSH, using the `username`/`password` of the API connection by default. When
   using an **API token**, `pve_ssh_username` becomes mandatory (a token is not a PAM user).
   A non-root SSH user needs password-less sudo:

   ```text
   terraform ALL=(root) NOPASSWD: /sbin/pvesm
   terraform ALL=(root) NOPASSWD: /sbin/qm
   terraform ALL=(root) NOPASSWD: /usr/bin/tee /var/lib/vz/*
   ```

   The node's `root` shell must be `bash`, and the node name must be resolvable (`ssh {
   node { name = "pve1", address = "10.0.0.1" } }` in the provider block if it is not).

4. **TLS.** Keep `pve_insecure = false` whenever the API certificate is valid. The provider
   never dials plain HTTP and negotiates at least `pve_min_tls`, which defaults to `1.3`: a
   node that only offers TLS 1.2 must either be upgraded or have `pve_min_tls = "1.2"` set
   explicitly.

5. **Outbound access from the node** to the image URLs (Debian CDN /
   `download.proxmox.com`), since the download happens on the Proxmox side.

### Workstation side

- `tofu` ≥ 1.6 and `ssh`/`ssh-agent` (or a PEM private key via `pve_ssh_private_key`).

## Quick start

```shell
cp terraform.tfvars.example terraform.tfvars   # then edit endpoint, node, keys, guests...

tofu init
tofu validate
tofu plan
tofu apply
```

Secrets can stay out of `terraform.tfvars` entirely by exporting them:

```shell
export TF_VAR_pve_api_token='terraform@pve!provider=00000000-0000-0000-0000-000000000000'
export TF_VAR_pve_password='...'   # only when using password authentication
```

Removing a guest from `var.vm`/`var.ct` and re-applying destroys it (VMs are **stopped**, not
shut down, thanks to `stop_on_destroy`), which avoids a destroy hanging on a guest agent that
is not running.

## Variables

### Proxmox VE connection

| Variable | Type | Default | Purpose |
|---|---|---|---|
| `pve_endpoint` | string | — | API URL, e.g. `https://pve.example.com:8006/`: HTTPS only, port 1–65535, without the `/api2/json` suffix. |
| `pve_username` | string | — | API user, e.g. `root@pam`. Keep it set even with a token (SSH fallback). |
| `pve_password` | string (sensitive) | `""` | Password authentication; ignored as soon as a token is set. |
| `pve_api_token` | string (sensitive) | `""` | `user@realm!token-name=uuid`; takes precedence over username/password. |
| `pve_node` | string | — | Node hosting every guest, image and snippet. |
| `pve_insecure` | bool | `false` | Skip TLS verification (self-signed API certificate only). |
| `pve_min_tls` | string | `1.3` | Minimum TLS version negotiated with the API (`1.0`–`1.3`); lower it only for an old node. |
| `pve_tmp_dir` | string | `""` | Custom provider temp directory (empty = system default). |
| `pve_random_vm_ids` | bool | `true` | Random, uniqueness-checked ids for guests that do not pin one. |
| `pve_ssh_agent` | bool | `true` | Use the local ssh-agent for the node SSH connection. |
| `pve_ssh_username` | string | `""` | SSH user on the node; **required with an API token**. |
| `pve_ssh_private_key` | string (sensitive) | `""` | PEM key used when no agent is available. |

### Datastores

| Variable | Type | Default | Purpose |
|---|---|---|---|
| `images_datastore_id` | string | `local` | Datastore receiving the VM images and LXC templates. |
| `snippets_datastore_id` | string | `local` | Datastore receiving the cloud-init snippets (snippets must be enabled). |
| `snippet_name_prefix` | string | `tofu` | Prefix of the two snippet file names; snippet names are datastore-wide. |

### Networking and access (shared by all guests)

| Variable | Type | Purpose |
|---|---|---|
| `dns_domain` | string | DNS search domain handed to the guests. |
| `dns_servers` | list(string) | IPv4 resolver addresses handed to the guests (IPv6 is not configured). |
| `gateway` | string | Default IPv4 gateway (ignored by `dhcp` entries). |
| `ssh_public_keys` | list(string) | Authorized keys for the VM admin user and the container root account. |
| `vm_admin_user` | string | Admin user created by cloud-init in the VMs (`debian` by default, the cloud image user). |

### `images` — managed OS images

Map of images downloaded once on the node; the key is what entries reference through
`vm_source_image` / `ct_source_image`.

| Attribute | Type | Default | Purpose |
|---|---|---|---|
| `content_type` | string | — | `iso` (VM disk image) or `vztmpl` (LXC template). |
| `url` | string | — | Versioned `http(s)://` download URL. |
| `file_name` | string | **required** | Name in the datastore: `.img`/`.iso` for `iso`, `.tar.zst`/`.tar.gz` for `vztmpl`. |
| `checksum` | string | `""` | Expected digest; hex, its length is checked against the algorithm; empty = no verification. |
| `checksum_algorithm` | string | `sha512` | `md5`, `sha1`, `sha224`, `sha256`, `sha384`, `sha512`. |

Defaults: `debian13` (VM, Debian 13), `debian12` (VM, Debian 12), `debian13-ct`,
`debian12-ct` (LXC templates).

### `vm` — virtual machines

| Attribute | Type | Default | Purpose |
|---|---|---|---|
| `vm_name` | string | — | VM name (also used by Proxmox as the guest hostname input). |
| `vm_ip` | string | — | `10.0.10.11/24` or `"dhcp"`. |
| `vm_datastore_storage_location` | string | — | Datastore for the VM disk. |
| `vm_source_image` | string | `debian13` | Key in `var.images` (must be an `iso` image). |
| `vm_description` | string | `Managed by OpenTofu` | VM description. |
| `vm_tags` | list(string) | `[]` | Proxmox tags (sorted automatically). |
| `vm_bridge` | string | `vmbr0` | Network bridge. |
| `vm_cores` | number | `2` | vCPUs. |
| `vm_cpu_type` | string | `x86-64-v2-AES` | Emulated CPU type. |
| `vm_memory` | number | `2048` | Memory (MiB). |
| `vm_floating_memory` | number | `0` | Balloon floor in MiB; `0` disables the balloon device. |
| `vm_disk_size` | number | `8` | Disk size in GiB; must be ≥ the cloud image virtual size. |
| `vm_nic_rate_limit` | number | `0` | NIC rate limit (MB/s), `0` = unlimited. |
| `vm_id` | number | auto | Pin the VM id when set (must be ≥ 100, unique, not used by a container). |
| `vm_protection` | bool | `false` | Set the Proxmox protection flag: the VM then cannot be destroyed. |
| `vm_recreate_on_cloud_init_change` | bool | `false` | Rebuild the VM (destroy + recreate, disks included) when the rendered cloud-init payload changes; toggling it rebuilds once. |

### `ct` — LXC containers

| Attribute | Type | Default | Purpose |
|---|---|---|---|
| `ct_name` | string | — | Container hostname. |
| `ct_ip` | string | — | `10.0.10.21/24` or `"dhcp"`. |
| `ct_datastore_storage_location` | string | — | Datastore for the container rootfs. |
| `ct_source_image` | string | `debian13-ct` | Key in `var.images` (must be a `vztmpl` template). |
| `ct_os_type` | string | `debian` | Proxmox container OS type (`debian`, `ubuntu`, `alpine`, ...). |
| `ct_description` | string | `Managed by OpenTofu` | Container description. |
| `ct_tags` | list(string) | `[]` | Proxmox tags (sorted automatically). |
| `ct_bridge` | string | `vmbr0` | Network bridge. |
| `ct_cores` | number | `1` | CPU cores. |
| `ct_memory` | number | `512` | Memory (MiB). |
| `ct_swap` | number | `0` | Swap (MiB). |
| `ct_disk_size` | number | `8` | Root filesystem size (GiB). |
| `ct_nic_rate_limit` | number | `0` | NIC rate limit (MB/s), `0` = unlimited. |
| `ct_id` | number | auto | Pin the container id when set (must be ≥ 100, unique, not used by a VM). |
| `ct_protection` | bool | `false` | Set the Proxmox protection flag: the container then cannot be destroyed or updated. |
| `ct_root_password` | string | `null` | Root password; leave unset for SSH-key-only access (it is stored in clear text in the local state). |

Every value is validated: IPs must be CIDR (or `dhcp`), sizes must be positive, DNS servers and
the gateway must be IPv4, keys must look like OpenSSH public keys, `ct_os_type` must be a Proxmox
container type, a pinned `vm_id`/`ct_id` must be ≥ 100, unique and not shared with the other
guest kind, and referencing an unknown or wrong-typed image key fails with an explicit message
(a `precondition`, evaluated during `plan`).

## Managed OS images

The images are downloaded **on the node** by the PVE `download-url` API (`images.tf`), so
nothing large transits through your workstation and no manual `wget` is needed. The default
entries are pinned to **versioned** Debian URLs with their `sha512` digest, because a `latest`
URL would invalidate the pinned checksum on every release.

### Refresh an image

1. Browse the release directory, e.g. <https://cloud.debian.org/images/cloud/trixie/> (VMs) or
   <http://download.proxmox.com/images/system/> (LXC templates).
2. Pick the new versioned file and its digest (`SHA512SUMS` next to the image, for Debian).
3. Update the matching entry in `var.images` (URL **and** `checksum` **and** `file_name`) —
   either in `terraform.tfvars` or in the defaults in `variables.tf`.
4. `tofu apply`: the new file is downloaded; guests referencing that key keep their existing
   disk until they are recreated.

Notes:

- `download.proxmox.com` serves the LXC templates over **HTTP** only for our purposes: its
  HTTPS certificate is not valid for the `download.proxmox.com` name, so use `http://` there.
- **The two LXC templates are the only unverified downloads of this project.**
  `download.proxmox.com` publishes no `SHA512SUMS` next to them, so `debian13-ct`/`debian12-ct`
  ship with an empty `checksum` (and `checksum_algorithm` alone is ignored by PVE): the archive
  that becomes the rootfs of every container is fetched over unauthenticated HTTP and is not
  verified, so a man-in-the-middle can substitute it. To close that hole, verify the template
  once out of band and pin the digest in your `terraform.tfvars`:

  ```shell
  curl -fsSLO http://download.proxmox.com/images/system/debian-13-standard_13.6-1_amd64.tar.zst
  sha512sum debian-13-standard_13.6-1_amd64.tar.zst
  ```

  then add `checksum = "<the sha512>"` to that entry of `var.images`; PVE verifies every later
  download against it.
- The `file_name` of a VM image must end with `.img` (or `.iso`): PVE rejects `.qcow2`.
- `file_name` is mandatory in every entry and doubles as the file identity in the datastore.
- `overwrite_unmanaged = true` makes the resource **delete** a same-named file that already sits
  in the datastore — including one this configuration did not create — and download the image
  again, instead of failing with "file already exists".

## How a guest is built

**Virtual machine** (`vms.tf`):

1. `proxmox_virtual_environment_download_file.image[<vm_source_image>]` provides the cloud
   image file id — the VM disk is imported from it over SSH (implicit dependency).
2. `proxmox_virtual_environment_file.user_config` renders `cloud-init/user-config.yaml.tftpl`
   (admin user `vm_admin_user`, `debian` by default, `ssh_public_keys`, DNS resolvers, password
   login disabled) and `vendor_config` installs `qemu-guest-agent`. Both snippets are named
   `<snippet_name_prefix>-user-config.yaml` / `<snippet_name_prefix>-vendor-config.yaml`.
   Renaming `snippet_name_prefix` replaces both snippet resources: the previous snippet files are
   destroyed with them (the provider deletes the file on destroy) and uploaded again under the
   new names. Only if that destroy is skipped or fails can a stale file remain on the datastore.
3. The VM boots with static IP + gateway and DNS from `initialization`; `agent.enabled = true`
   is required for the provider to report `vm_ipv4_addresses`.

> A custom user config **replaces** the user data Proxmox generates (the Proxmox-side user,
> password and SSH keys are not used for VMs); that is exactly why the template defines the
> admin user, the sudo rule and the authorized keys. The `network` and `meta` configs remain
> auto-generated by Proxmox. A shared snippet cannot set a per-VM hostname: if you need one,
> use `for_each` to render one snippet per VM or set it inside the image.

> **User and vendor data are applied once, at the guest's first boot.** Editing
> `ssh_public_keys`, `vm_admin_user`, `dns_domain` or `dns_servers` updates the snippet and shows
> up in `tofu plan`, but a VM that already booted keeps its keys and `/etc/resolv.conf`: a
> revoked key stays authorized until the guest is rebuilt. Set
> `vm_recreate_on_cloud_init_change = true` on a VM to have OpenTofu rebuild it whenever the
> rendered payload changes — the variables above **and** the template files
> (`cloud-init/user-config.yaml.tftpl`, `cloud-init/vendor-config.yaml`) — or rebuild it
> explicitly:
>
> ```shell
> tofu apply -replace='proxmox_virtual_environment_vm.debian_vm["web-01"]'
> ```
>
> Three consequences of that flag:
>
> - the rebuild **destroys** the VM before recreating it, disks included: anything stored inside
>   the guest is lost (keep the data on a separate volume, or take a backup first);
> - the flag is part of the rebuild trigger, so **toggling it** (`false` → `true` or `true` →
>   `false`) rebuilds that VM once;
> - it is incompatible with `vm_protection = true`: Proxmox refuses to remove a protected VM, so
>   the rebuild fails — clear the protection flag first.
>
> Containers are unaffected: their DNS settings and root keys are written by the provider, not
> by cloud-init.

**Container** (`containers.tf`):

1. The rootfs is created from
   `proxmox_virtual_environment_download_file.image[<ct_source_image>]`.
2. `initialization` sets the hostname, DNS, static IP/gateway and the root account
   (`ssh_public_keys`, optional `ct_root_password`).
3. The container is **unprivileged** with `nesting = true` (fuse disabled).

|---|---|
| `vm_ids`, `vm_names` | Maps keyed by the `var.vm` key. |

## Verification

No live Proxmox access is needed to check the configuration:

```shell
tofu fmt -check -recursive   # formatting (exit code 0 expected)
tofu init -backend=false
tofu validate                # syntax, types, variable and precondition wiring
```

`tofu plan`/`apply` require real credentials and will create resources on the node.

## Orchestrator wrapper (`lib_tofu.sh`)

`lib_tofu.sh` drives this project through the `my_warp.sh` orchestrator, so the same commands work
locally and from CI:

```shell
${MY_GIT_DIR}/shell/my_warp.sh --lib tofu <command> [options]
```

| Command | What it runs |
|---|---|
| `tofu_version` | `tofu version`. |
| `tofu_init` | `tofu init -backend=false` (`--backend true` for a full init). |
| `tofu_fmt` | `tofu fmt -recursive`; with `--dry-run`: `fmt -check -recursive -diff`. |
| `tofu_validate` | `tofu validate`. |
| `tofu_plan` | `tofu plan -input=false` (`--var-file`, `--out`; `--dry-run` ignores `--out`). |
| `tofu_apply` | `tofu apply -auto-approve` — **requires `--force`**; `--dry-run` only shows the plan. |
| `tofu_destroy` | `tofu destroy -auto-approve` — **requires `--force`**; `--dry-run` only shows the destroy plan. |
| `tofu_output` | `tofu output -json` (`--name <output>` for a single one). |
| `tofu_state_list` | `tofu state list`. |
| `tofu_show` | `tofu show -json` (`--file <plan>` to inspect a saved plan). |
| `tofu_check` | The read-only gate: `fmt -check -recursive -diff` then `validate`. |
| `tofu_vars_doc_check` | Offline check that every `variables.tf` variable is documented in `README.md` and `terraform.tfvars.example`. |

```shell
# read-only gate, no credentials needed
${MY_GIT_DIR}/shell/my_warp.sh --lib tofu tofu_check

# never mutate blindly: preview first, then force
${MY_GIT_DIR}/shell/my_warp.sh --lib tofu --dry-run tofu_apply
${MY_GIT_DIR}/shell/my_warp.sh --lib tofu --force tofu_apply

# work on another variable file
${MY_GIT_DIR}/shell/my_warp.sh --lib tofu tofu_plan --var-file lab.tfvars
```

Settings live in `conf/tofu.conf` (`TOFU_BIN`, `TOFU_DIR`, `TOFU_VAR_FILE`) and the environment
always wins, so `TOFU_DIR=/srv/tofu ${MY_GIT_DIR}/shell/my_warp.sh --lib tofu tofu_fmt` works too.
`--var-file` accepts an absolute path or a path relative to the project directory: it is resolved
to an absolute path before being handed to `tofu`, so the file that is checked is the file that is
used. `plan`/`apply`/`destroy` always run with `-input=false`, so a missing variable fails
immediately instead of prompting.
`--force` (or `TOFU_CONFIRM=true`) is the only way `tofu_apply`/`tofu_destroy` will run: the
wrapper never auto-approves on its own, and `--dry-run` always stays read-only.

## Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `no file exists at cloud-init/...` | A snippet source file is missing — check `cloud-init/`. |
| Snippet upload fails with a permission/sudo error | Snippets are not enabled on the datastore, or the SSH user lacks the `NOPASSWD` sudo rules listed above. |
| `only root can set 'arch' config` / `user != root@pam` | Some operations are refused for API tokens: use `root@pam` password authentication for those runs. |
| `Plan`/`Refresh` hangs for minutes, then times out | `agent.enabled = true` while `qemu-guest-agent` is not running in the guest. The vendor data installs it; a disk check in the guest can also delay it. `stop_on_destroy` keeps destroys from hanging. |
| Tags show a permanent diff | Tags are sorted by Proxmox; the resources apply `sort()` accordingly — keep `ct_tags`/`vm_tags` free of duplicates. |
| `wrong file extension .qcow2` | PVE accepts only `.img`/`.iso` for `iso` content type: rename through `file_name`. |
| `disk size ... too small` | `vm_disk_size` must be ≥ the cloud image virtual size (default `8` GiB). |
| Guest unreachable after `apply` | Check the QEMU agent status, `tofu output vm_ipv4_addresses`, and that the guest started (`tofu plan` shows `started`). |
| TLS handshake failure with an older API | The provider negotiates at least `pve_min_tls` (`1.3` by default), so a TLS 1.2-only node is refused. Upgrade the Proxmox TLS setup, or set `pve_min_tls = "1.2"` as a deliberate downgrade. |
| New SSH keys / resolvers not applied to an existing VM | cloud-init user and vendor data run at the first boot only: rebuild the VM (`tofu apply -replace=...`) or set `vm_recreate_on_cloud_init_change = true` — note that a rebuild **destroys** the VM and its disks. |
| Destroy (or update) refused by Proxmox | The guest has `vm_protection`/`ct_protection = true`: set it back to `false`, apply, then destroy. |
| `you must specify a valid endpoint` / plain `http://` rejected | `pve_endpoint` must be an HTTPS URL such as `https://pve.example.com:8006/`. |

## State

State is **local** (`terraform.tfstate` in this directory) and git-ignored, together with
`*.tfvars` (which hold the API token and the passwords). Two consequences worth knowing:

- Keep a backup of the state file: it is the only record linking the configuration to the
  guests (the lock file `.terraform.lock.hcl` *is* tracked — it pins the exact provider version
  and its checksums).
- The state is stored **in clear text** and contains `ct_root_password` when you set it. Leave
  `ct_root_password` unset to keep SSH-key-only access, or move to a remote backend if the
  file must leave your machine.
- Saved plan files (`tofu plan -out=...`, `*.tfplan`/`plan.out`) embed the variable values in
  clear text too: they are git-ignored and deserve the same care as the state file.
